# Debugger та breakpoints у N0x CLI (дорожня карта)

Напрям **`debug`** — **додаток** до ядра N0x: можна використовувати весь звичайний CLI (`mem`, `function trace`, `ir`, …) **без будь-якого** debug. Для **агентських** сценаріїв нижній розділ **«Робочий цикл під керування ШІ»** описує один виклик із зупинкою й JSON-звітом.

**Ціль дорожньої карти:** розширення (Hardware BP, множинні точки, інтерактивний `continue`) **не є обовʼязком** для користувача — лише для тих задач, де CE/another debugger не хочеться використовувати.

### Що вже реалізовано в crates

- **`n0x debug await-hit`** (**Windows**, ціль — **64-bit процес**, бінарій CLI збираний як **x86_64**): `DebugActiveProcess` + програмний **`int3`** по VA (`--module` + `--addr` або **`--addr-rva`**), блокування до відповідного **`EXCEPTION_BREAKPOINT`** або **`--timeout-ms`**, відновлення байта та **`DebugActiveProcessStop`**.
  - Після INT3 процес звичайно має **`Rip`** уже **за збереженим байтом**; якщо лише повернути оригінал і `ContinueDebugEvent` без **відкату `Rip`** на **`bp_va`**, многобайтна інструкція декодується з середини й гра часто впаде (**`EXCEPTION_ACCESS_VIOLATION`**, топ кадру часто лише на кілька байт нижче за точку).
  - Прогнозний JSON успіху: **`data.schema`** = **`n0x.debug.await_hit.v1`**, вкладений **`hit.schema`** (якщо є збіг) = **`n0x.debug.hit.v1`**; **`timedOut`** при таймауті.
  - **`--report`**: NDJSON з **`schema`:** **`n0x.debug.await_hit.report.v1`** (`kind`: `session_start` \| `awaiting_user` \| `hit` \| `timeout`).
- Перед використанням: **закрити** інший відладчик для цього PID; без прав адміна або при античиті доступ можливий із відмовою.

### Чого ще немає (далі цей файл — план розширень)

### 1. Режим налагоджувача замість простого доступу памʼяті

- **`DebugActiveProcess`** (або створення процесу з **`DEBUG_PROCESS`**) або окремий підкомандний контекст `debug attach --pid`.
- Основний цикл: **`WaitForDebugEvent`** / **`ContinueDebugEvent`** з таймаутом і graceful detach.
- **Узгодження з поточним `target attach`:** або окремий шлях «debug session», або чітко заборонені одночасно два режими на один PID.

### 2. Програмний breakpoint (`int3`, `0xCC`)

- Підмінити байт за VA (зберегти оригінал для restore).
- Після першого збігу — опціонально **продовжити** (повернути байт і single-step через **`EXCEPTION_SINGLE_STEP`**), або лишити зупиненим до **`debug continue`**.
- Параметри: `--once` | `--sticky`, `--threads all|tid`, ліміт **N** збігів потім автозлітання.

Це найпростіший шлях зловити вхід у відому інструкцію (аналог «breakpoint on execute» у CE).

### 3. Апаратні breakpoints (опційно, складніше)

- **Execute / write / read-write** на 1–4 адресах через **DR0–DR3** + відповідні біти в **DR7** на цільовому потоці (**`SetThreadContext`** / kernel path у hi-perf сценаріях).
- Обмеження: **лише 4 адреси**, вирівнювання для watchpoint-ів, взаємодія з іншими відладчиками та частина античитів.

Корисно для **watch** на поле структури без сканування `int3` по всьому модулі.

### 4. Вихід у JSON (контракт для агентів)

Після кожного збігу (або пакетом по завершенню):

- **`hitIndex`**, **`exceptionCode`**, **`threadId`**, **`address`**, **`breakpointId`**.
- Знімок **`registers`** (мінімум RIP/RSP + загальні 64-бітні; опційно XMM).
- **`stack`**: сирий зріз `[RSP..]` **або** обмежений unwind (якщо буде інтеграція з існуючими PE/DWARF/універсальним евристичним unwinder — окреме рішення).
- **`modules`** (кешований base map) для перетворення VA → `module+RVA` у відповіді.

Схема на кшталт **`n0x.debug.hit.v1`** (окремо зафіксувати в [[../CLI_FEATURES_SPEC|CLI Spec]] під час імплементації).

### 5. CLI-обгортка (чернетка UX)

```
n0x debug attach --pid <PID>
n0x debug break set --addr <VA|module+rva> [--rva] [--kind sw|hw-exec|hw-write] [--size 1|2|4|8 hw-only]
n0x debug break list
n0x debug break clear --id <ID>|--all
n0x debug run --until-hit --max-events 1 --timeout-ms <n> [--report <.ndjson>] --json
n0x debug continue
n0x debug detach
```

Інтерактивний TUI — не обовʼязковий на першому етапі; **blocking `run --until-hit`** + **структурований звіт** — базовий сценарій для агента.

## Робочий цикл під керування ШІ (мінімальне втручання людини)

**Ідея:** людина **не** відкрива CE і не «ставить breakpoint руками». Агент викликає CLI; оператор лише виконує **коротку інструкцію з природньою мовою** («у лобі 4/4, один раз натисни Add Bot»), яку підготував або сам агент, або видав сам CLI перед очікуванням.

### Ролі

| Роль | Що робить |
|------|-----------|
| **ШІ / агент** | Обчислює PID/mod/RVA, викликає `debug attach` → `break set` → `run --until-hit` (або один составний **`debug await-hit`** нижче), читає **JSON/NDJSON звіт**, аналізує stack/реєстри — далі патч або нова точка збігу. |
| **Людина** | Тільки **дії всередині гри/UI**, недоступні для автоматизації без інжекцій/нейромережі кліків. |
| **CLI** | Тримає debug loop із **гарантованим таймаутом**, завжди **відновлює** патчені байти / BP при успіху, таймауті або `detach`. |

### Контракт для агента (обовʼязково передбачити в імплементації)

1. **Детермінований вихід на stdout**: основний результат — **`ok` + `data`** у тому самому загальному форматі, що й решта команд N0x, щоб парс був однаковим у промпті агента.
2. **До початку очікування** у `data` зʼявляється поле типу **`awaitUser`** (рядки українською або нейтральною мовою, що повторимо в промпті до людини) — **людині не потрібно заглядати у CE**.
3. **Після збігу** — один блок **`hits[]`** або посилання **`reportPath`**; кожний hit узгоджений з **`n0x.debug.hit.v1`** (регістри, необовʼязково unwind, топ стеку, `module+rva` для RIP).
4. **`TIMEOUT`** — не «зависання»: **`ok:false`** або `ok:true` з `timedOut:true` та порожніми `hits` (зафіксувати одну модель і не міняти без версії схеми); при цьому **cleanup breakpoints обовʼязковий**.
5. **Паралель до `function trace`**: опційний **`--report`** (NDJSON, як `--report` у trace) — потокові події `{kind: session_start|awaiting_user|hit|timeout|detach}` для довгої сесії з кількома збігами.

### Спрощена команда (цільові UX)

Обʼєднати у **одну** неквазіінтерактивну операцію для промпту агента:

```text
n0x debug await-hit --pid <PID>
  [--module X --addr-rva --addr <RVA>]
  [--instruction-file path.txt]
  [--timeout-ms <n>]
  [--report <hits.ndjson>]
  [--json]
```

Семантика:

- attach → sw break (або hw, якщо задано) → вивести в JSON **`awaitUser`** (текст з `--instruction-file` або з параметра `--instruction "..."`) → блокуюче **`WaitForDebugEvent`** до першого збігу або таймауту → зібрати знімок → **detach + restore** → OK + `data`.

Це вирізає проміжкові людські помилки («забули continue» у відладчикі).

### Принцип для агентських сценаріїв (не заборона для людей)

- Агенту зазвичай простіший **повний конвеєр у одному CLI-виклику**, ніж паралельно CE + ручний `continue`.
- При **`--quiet`** основна людиноорієнтовна підказка — **`awaitUser`** у **`--json`** виході або в **`--report`** NDJSON, а не довгі рядки в stderr.

## Ризики та обмеження (явно документувати в `--help`)

- **Один активний налагоджувач**: another debugger вже підключені — друга сесія зазвичай не вдалася або непередбачувана.
- **DRM / античит**: гри можуть забороняти `DebugActiveProcess`; потрібен чіткий **помилковий результат** у JSON (`ok: false`, причина `ACCESS_DENIED`, `UNSUPPORTED`).
- **WOW64**, змішані **x86/x64**, дочірні процеси та **JOB objects** — окремі гілки тестування.
- **Безопасність**: запис `0xCC` або HW BP у чужому процесі = той же клас ризику, що `mem write`; залишити в рамках існуючої політики patch/write.

## Критерій для наступних розширень (beyond `await-hit`)

Мінімальний **`await-hit`** конвеєр уже реалізований. Нижче — **наступні можливі розширення**:

- Інтерактивний **`attach` / `detach` / `break list`** без повного одноразового конвеєра.
- Апаратний BP або **мульти-збіги** в одній сесії.

**Що вже закрито в `await-hit`:** один x64 user-mode процес; один SW breakpoint (**`int3`**) за **`--addr`** або **`--module` + `--addr-rva`**; один збіг → JSON **регістри** + **qword-и зі стеку** + **відновлення** байта перед detach; поля **`awaitUser`**, **`timedOut`**, приклад у [[README]].

### Обмеження поточної реалізації (`await-hit` v1) — зафіксовано

- **Один** виконуємий breakpoint (один байт **`0xCC`**); без **hardware** BP і без окремих субкоманд **`attach` / `continue` / `detach`** у одній сесії (усе в одному виклику).
- **Один активний відладчик** на PID: не тримати **another debugger** на тому ж процесі одночасно з `await-hit`.
- Цільовий процес має бути **нативний x64** (`detect_arch` → **`x64`**); **WOW64 / 32-bit** цілі явно відхиляються.
- Помилки Win32 на ранніх кроках: частково мапляться в **`error.code`** у відповіді (`DEBUG_ATTACH_DENIED_OR_BUSY`, `PROCESS_OPEN_DENIED`, …); повний переклад **`GetLastError`** у числовий/іменований код для агента — **у планах** (див. «План» нижче).

### План (наступні ітерації)

- Розширити **`ok: false`**: стабільні коди + опційно **`win32LastError`** / **`ntStatus`** у JSON для всіх гілок `debug await-hit` (не лише евристика по тексту повідомлення в `main`).
- HW breakpoints, кілька точок, інтерактивний debug loop — як у розділах 1–5 вище.

У [[BACKEND_SPEC]] уже згадано сервіс **Debugger** — ця дорожня карта задає очікувану поверхню для нативного шару перед Tauri/UI.
